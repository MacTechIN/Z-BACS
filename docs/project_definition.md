## 1. 한 문장 정의

> **파일 소유자가 BSA(Blockchain Secure Authentication) 기반 패스워드리스 암호화를 걸어 둔 파일을 누구에게 전달하더라도, 그 파일이 열리는 순간 소유자에게 실시간 승인을 요청하고, 승인된 권한(읽기전용 / 편집 / 거부) 범위 안에서만 자동 복호화되어 사용되며, 사용이 끝나 저장되면 다시 원래대로 암호화되어 다음 열람 시 재승인을 요구하는 BSA 기반 원격 파일 관리 솔루션.**

## 2. 배경과 문제 정의

### 2.1 현재의 문제
- 파일은 한 번 전달되면 소유자의 통제를 완전히 벗어난다. (복사·재전달·무기한 열람)
- 기존 문서 DRM(Fasoo, MarkAny 등)은 **중앙 정책 서버**와 **기업 내부 배포**를 전제로 하며, 개인·소규모 조직·조직 간 전달에 적용하기 어렵다.
- 비밀번호 기반 파일 암호화(ZIP 암호, PDF 암호)는 비밀번호 자체가 함께 전달되므로 통제 수단이 아니다.
- 승인 이력이 남지 않아 "누가 언제 열었는가"를 사후에 증명할 수 없다.

### 2.2 Z-BACS가 제공하는 답
1. **소유자 중심 통제(Owner-in-the-loop)**: 파일을 여는 모든 시도는 소유자의 실시간 승인을 통과해야 한다.
2. **패스워드리스**: 비밀번호를 만들지도, 공유하지도 않는다. 소유자는 기기 생체인증(BSA / 패스키)으로 승인한다.
3. **자체 실행(Self-carrying)**: 파일 자체가 열람기(Agent)를 함께 가지고 다니거나 즉시 설치하도록 유도하여, 수신자가 별도 준비 없이 열 수 있다. (Windows 우선, 이후 macOS/Linux)
4. **저장 시 자동 재암호화**: 편집 후 저장하면 다시 봉인되며, 다음 열람은 다시 승인이 필요하다.
5. **불변 감사 로그**: 승인·거부·열람·저장 이벤트가 블록체인(또는 분산 원장)에 기록되어 부인 방지된다.
6. **영지식/프라이버시**: 승인 사실은 공개 검증 가능하지만, 파일 내용·소유자 신원·요청자 신원은 온체인에 노출되지 않는다.

## 3. 목표 (Goals)

| ID | 목표 | 측정 기준 |
|---|---|---|
| G1 | 소유자가 파일 1개를 3클릭 이내에 봉인(Seal)할 수 있다 | UX 테스트 |
| G2 | 수신자가 봉인 파일을 열면 소유자에게 10초 이내에 승인 요청이 도달한다 | 푸시 지연 측정 |
| G3 | 소유자 승인 후 5초 이내에 수신자 화면에서 파일이 열린다 (L2 체인 기준) | E2E 지연 측정 |
| G4 | 승인 유형: **거부 / 읽기전용 / 편집가능** + 시간·횟수 제한 | 기능 테스트 |
| G5 | 편집 후 저장 시 평문이 디스크에 잔존하지 않고 재암호화된다 | 포렌식 검증 |
| G6 | 소유자의 비밀번호·개인키가 서버 또는 체인에 저장되지 않는다 | 코드/아키텍처 리뷰 |
| G7 | 모든 승인 이벤트가 온체인 감사 로그로 남는다 | 체인 조회 |
| G8 | Windows 10/11 에서 파일 더블클릭만으로 동작한다 | 설치 테스트 |

## 4. 비목표 (Non-Goals, 1차 릴리스 범위 밖)

- 화면 캡처·카메라 촬영 방지 (아날로그 홀은 소프트웨어로 막을 수 없다)
- 완전한 오프라인 열람 (승인은 온라인이 전제)
- 자체 블록체인 메인넷 운영 (기존 L2/프라이빗 체인 사용)
- 모바일(iOS/Android)에서의 파일 열람기 (승인 앱은 모바일 포함, 열람기는 데스크톱 우선)
- 커널 드라이버 기반 투명 암호화 (3단계 이후 옵션)

## 5. 이해관계자와 역할

| 역할 | 설명 |
|---|---|
| **Owner (소유자, Alice)** | 파일을 봉인하고 승인 권한을 가진 사람. Z-BACS Agent + 승인 앱(모바일/데스크톱) 보유 |
| **Recipient (수신자, Bob)** | 봉인 파일을 전달받아 열람/편집을 원하는 사람. Z-BACS Agent 필요 |
| **Z-BACS Agent** | 데스크톱 상주 프로그램. 봉인·개봉·재봉인·승인 요청·감사 기록을 수행 |
| **Approval App** | 소유자가 승인/거부하는 앱. BSA Authenticator 또는 패스키 기반 자체 앱 |
| **Relay / Coordinator** | 요청·승인 메시지를 중계하는 서비스. 평문·키를 절대 보지 못하는 무신뢰 설계 |
| **Ledger (체인)** | 파일 등록, 승인 기록, 정책 앵커. EVM L2(Base 등) 또는 프라이빗 체인 |
| **Guardian Nodes (3단계)** | 임계값 프록시 재암호화 노드. 소유자 오프라인 시 정책 기반 위임 |

## 6. 핵심 사용자 시나리오

### 시나리오 A: 봉인(Seal)
1. Alice가 `report.docx`를 우클릭 → "Z-BACS로 봉인".
2. Agent가 파일별 데이터키(DEK)로 파일을 암호화하고, DEK를 Alice의 소유자 키로 봉인한다.
3. 체인에 파일 지문(해시 커밋)과 소유자 계정을 등록한다. (내용·파일명은 미노출)
4. 결과물 `report.docx.zbacs` (또는 Windows용 자체실행 `report.zbacs.exe`) 생성.

### 시나리오 B: 열람 요청 및 승인
1. Bob이 `report.docx.zbacs`를 더블클릭. Agent가 없으면 부트스트랩 스텁이 설치를 안내/수행한다.
2. Agent가 Bob의 기기 키를 생성/사용하여 **접근 요청**을 서명하고 Relay로 전송한다.
3. Alice의 승인 앱에 푸시 도착: "Bob(기기 X)이 report.docx 열람 요청. [거부] [읽기전용] [편집가능] · 유효 시간: 1시간".
4. Alice가 생체인증(BSA/패스키)으로 승인 → EIP-712 구조화 서명 + 온체인 승인 기록.
5. Alice의 Agent(또는 승인 앱)가 DEK를 **Bob의 기기 공개키로 재봉인(HPKE)** 하여 전달한다.
6. Bob의 Agent가 승인 조건을 검증하고 보호 작업공간에서 복호화 → 기본 앱으로 열기.

### 시나리오 C: 사용 후 저장 (편집가능)
1. Bob이 편집 후 저장 → Agent가 파일 변경을 감지.
2. 앱 종료 또는 세션 만료 시 새 DEK로 재암호화, 새 버전으로 봉인, 평문 안전 삭제.
3. 새 버전 해시를 체인에 기록(버전 체인). Alice에게 "새 버전 생성" 알림.
4. 다음 열람 시 다시 승인 필요.

### 시나리오 D: 읽기전용
- 파일은 읽기전용 속성으로 열리고, 세션 종료 시 평문 삭제. 변경분은 폐기된다.

### 시나리오 E: 거부 / 만료 / 회수
- 거부 시 Bob 화면에 사유 표시, 온체인 거부 기록.
- 유효 시간이 지나면 Agent가 세션을 종료하고 재봉인.
- Alice는 언제든 "회수(Revoke)"로 진행 중인 세션 권한을 종료할 수 있다.

## 7. 기능 요구사항 (FR)

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-01 | 임의 파일을 AES-256-GCM 또는 XChaCha20-Poly1305로 봉인 | 필수 |
| FR-02 | 봉인 파일은 자체 컨테이너 포맷(`.zbacs`)을 가지며 메타데이터·정책·키봉투를 포함 | 필수 |
| FR-03 | Windows에서 `.zbacs` 더블클릭 시 Agent가 실행됨 (파일 연결) | 필수 |
| FR-04 | Agent 미설치 환경을 위한 자체실행 래퍼(`.exe`) 생성 옵션 | 필수(Win) |
| FR-05 | 열람 시 소유자에게 실시간 승인 요청(푸시) | 필수 |
| FR-06 | 승인 유형: 거부 / 읽기전용 / 편집가능 | 필수 |
| FR-07 | 승인 조건: 유효시간, 열람 횟수, 기기 고정 | 필수 |
| FR-08 | 소유자 승인은 BSA 또는 패스키(WebAuthn) 생체인증으로 수행 | 필수 |
| FR-09 | 승인 서명은 EIP-712 구조화 데이터로 소유자가 내용을 확인 가능 | 필수 |
| FR-10 | 승인/거부/열람/저장 이벤트의 온체인 감사 기록 | 필수 |
| FR-11 | 편집 후 저장 시 자동 재암호화 및 평문 안전 삭제 | 필수 |
| FR-12 | 버전 관리: 재봉인 시 새 버전, 이전 버전 해시 체인 연결 | 필수 |
| FR-13 | 소유자 회수(Revoke)로 활성 세션 즉시 종료 | 필수 |
| FR-14 | 소유자 기기 분실 시 복구(소셜 복구 / 다중기기) | 권장 |
| FR-15 | 소유자 오프라인 시 사전 정책 기반 자동 승인(PRE/임계값) | 3단계 |
| FR-16 | macOS / Linux Agent | 2단계 |
| FR-17 | 온체인 프라이버시: 파일명·내용·신원 미노출, ZK 멤버십 증명 | 3단계 |
| FR-18 | 스마트 컨트랙트 AI 감사 파이프라인(Hugging Face 모델) CI 통합 | 권장 |

## 8. 비기능 요구사항 (NFR)

| ID | 요구사항 |
|---|---|
| NFR-01 | 승인 왕복 지연 ≤ 5초 (L2 기준), 로컬 복호화 100MB 파일 ≤ 2초 |
| NFR-02 | 평문은 메모리 또는 소유자 전용 ACL의 보호 작업공간에만 존재, 세션 종료 시 즉시 삭제 |
| NFR-03 | Relay는 무신뢰: 평문·DEK·개인키를 절대 취급하지 않음 |
| NFR-04 | 모든 암호 프리미티브는 검증된 라이브러리 사용 (RustCrypto, libsodium, age 등). 자체 구현 금지 |
| NFR-05 | 코드 서명된 바이너리 배포(Windows Authenticode), SmartScreen/AV 오탐 최소화 |
| NFR-06 | 오픈소스 라이선스 호환 (MIT/Apache-2.0/BSD 우선, GPL은 별도 검토) |
| NFR-07 | 감사 로그는 개인정보를 포함하지 않는 커밋(해시)만 온체인 |
| NFR-08 | 스마트 컨트랙트는 업그레이드 가능 프록시 + 타임락, 배포 전 정적 분석 + AI 감사 |

## 9. 신뢰 모델과 명시적 한계

**보호 대상 위협**
- 파일 탈취(전달 경로·저장소 유출) → 암호화로 무력화
- 무단 열람·재전달 → 소유자 승인 없이는 개봉 불가
- 승인 위조·재전송 → 일회용 nonce + 서명 + 온체인 기록
- 중앙 서버 침해 → Relay·체인 모두 키를 보관하지 않음

**보호할 수 없는 위협 (정직하게 명시)**
- 승인받은 수신자가 화면을 촬영·캡처하거나 내용을 옮겨 적는 행위
- 수신자 기기에 관리자 권한을 가진 공격자가 메모리를 덤프하는 행위 (TEE 없이는 완화만 가능)
- 수신자가 승인 세션 중 다른 앱으로 "다른 이름으로 저장"하는 행위 → 1·2단계에서는 탐지·기록, 3단계 미니필터 드라이버로 차단

> Z-BACS는 **"승인 없이 열 수 없다"**를 암호학적으로 보장하고, **"승인 후의 오남용"**은 억제·탐지·기록한다. 이 구분을 모든 문서와 마케팅에서 유지한다.

## 10. 성공 기준 (MVP Definition of Done)

1. Windows 두 대(Alice, Bob) 사이에서 시나리오 A~E 전부 동작.
2. 소유자 승인이 패스키(Windows Hello) 또는 BSA 샌드박스 SDK로 수행됨.
3. Base Sepolia(또는 로컬 Anvil)에 승인 이벤트 기록·조회 가능.
4. 평문 잔존 검증: 세션 종료 후 디스크 스캔에 원본 내용 없음.
5. 위협 모델의 필수 완화 항목이 모두 구현되고 테스트됨.
